# XHS CAST 2.0

把一份材料拆解成层次清楚的多页小红书卡片，让读者更快看懂你想传达的内容。

它会根据材料安排信息顺序、页数、页序、标题和上屏文案，并检查封面、各页标题与正文是否互相对应。

它交付的是卡片规划方案，不代替最终制图、发布或效果验证。需要把方案制作成实际图片时，建议使用 [$guizang-social-card-skill](https://github.com/op7418/guizang-social-card-skill)（归藏老师的制卡 Skill）。

## 适合什么内容

XHS CAST 适合把已有内容重新组织成多页卡片：

- GitHub 项目、AI 工具、产品或服务介绍
- 教程、方法、观点、案例、复盘和资源清单
- 日报、新闻和行业快讯
- 已有卡片方案的审查与重构

当材料不少，但页面像功能目录、前后没有承接、标题说不清每页重点时，可以用它重新规划。

## 你会得到什么

一次完整规划通常包含四部分：

| 产物 | 内容 |
| --- | --- |
| 传播策略摘要 | 目标读者、传播目标、核心价值、证据状态、阅读路径、行动入口和待确认项 |
| 整组页序 | 按读者需要经历的信息变化安排页数，不按文档章节或功能列表机械拆页 |
| 逐页卡片方案 | 页面任务、读者新增信息、来源锚点、上屏文字、信息层级、重点词和承接动作 |
| 制卡交接 | 构图意图、证据素材、制作限制和制作规则（Recipe），供后续制卡环节使用 |

用户明确需要时，还可以继续生成与卡片采用同一主张和证据上限的小红书笔记。

## 工作流程

```text
提供材料
  -> 确认传播方向与取舍
  -> 划定来源和证据边界
  -> 设计读者路径，决定页数
  -> 定义每页职责，写标题和上屏文字
  -> 对账封面、页面标题、正文和交付内容
```

封面要概括整组内容；每页标题要说明本页新增的信息；正文必须直接解释、证明或落实标题作出的承诺。

## 正式规划前，先确认方向

新的正式规划或完整重写，默认先给出方向确认单。每个选项都要说明：

| 确认项 | 会说明什么 |
| --- | --- |
| 适用场景 | 为什么当前材料适合这个方向 |
| 内容组织 | 会按什么顺序讲，哪些内容保留，哪些内容舍弃 |
| 最终交付 | 选择后会得到什么，读者能带走什么信息 |
| 关键取舍 | 与其他方向相比，重点和证据门槛如何变化 |

例如，一份日报可以有以下三种做法：

| 方向 | 选择后怎么组织 | 最终交付 | 主要取舍 |
| --- | --- | --- | --- |
| 新闻速览 | 按时间或原始栏目，逐条说清主体、动作、对象和状态 | 一组多页快讯，读者知道本期发生了什么 | 覆盖面较广，单条背景较少；适合多条消息 |
| 单条深挖 | 围绕一个事件补足背景、直接证据和边界 | 一条消息讲透的专题卡片 | 舍弃其他条目，换取理解深度 |
| 跨条目判断 | 先筛出真正可比的条目，再提出带限制条件的共同判断 | 有证据边界的趋势或判断卡片 | 证据门槛最高，不能把不同机制硬合并 |

默认推荐方向必须说明推荐理由。用户可以确认、修改字段、输入自定义方向，或明确要求跳过确认。

没有明确确认前，只展示方向确认单，不生成完整策略、页序或逐页文案。只有在当前请求中明确写出“跳过确认”“不用问”或“直接生成”时，才会跳过这一步。

仅询问这个 Skill 能做什么、文件如何组成或输出长什么样时，不启动方向确认。把 XHS CAST 自身规划成卡片，仍属于正式规划，默认先确认方向。

## 交互方式

XHS CAST 会按当前宿主实际具备的能力提供交互：

| 当前运行条件 | 处理方式 |
| --- | --- |
| 宿主提供可回传的原生选择控件 | 使用原生控件 |
| Codex 中 `visualize` 可用，且当前对话能够接收选择回传 | 使用可点击的方向选择面板 |
| 没有可用控件，且任务确实需要用户选择 | 本次任务首次提示可安装或启用 `visualize`，同时提供编号选项继续 |
| 面板能显示但无法回传、回传报错或超时 | 视为尚未确认，降级为同一份编号确认单 |
| 用户已明确要求直接生成，或当前任务不需要选择 | 不提示安装，也不要求交互 |

不会自动安装插件，也不会把面板上的选中状态当作用户确认。同一任务内已经提示过安装后，不重复提示。

视觉面板、原生控件和编号选项必须提供相同的选项说明、内容组织、最终交付和关键取舍。Claude 等已提供原生交互的宿主，不显示 Codex 插件安装提示。

## 日报与新闻模式

日报和新闻材料先分清三层：

- 导语是编辑框架
- 栏目标题是分类
- 条目正文才是事件本身

新闻页标题优先写清楚事实：

```text
主体 + 具体动作或事件 + 对象或状态
```

“依据”“为什么”“证据性质”“应用”可以放在副标题或收尾，不能代替事件标题。

封面若承诺了数量、主体数、时间范围或“这周 / 本期”等信息，后续页面必须逐项兑现；无法兑现时，应降低或删掉这项承诺。

多主体材料还要区分不同机制。访问边界、动作权限、交付复核、研究方向和个人建议不能只因出现在同一时期，就被压成同一种做法或同一个行业结论。

## 证据边界

XHS CAST 会区分“产品被设计成这样”和“产品已经在现实中产生了某种效果”。

- 原始帖子、官方文档、真实产物和原始数据，只支撑其明确范围内的主张。
- 日报摘要和编辑总括可用于定位与组织，不能自动证明细节、因果关系或行业共识。
- Beta、试用、研究、招聘、公司自述部署和个人实测，不能写成普遍可用的能力。
- 缺少案例、数据或独立评测时，不补写用户故事、效果数字或“更安全”“更高效”等结论。
- 目标读者场景、当前替代方案、读者疑虑或关键证据尚未确认时，会标记为“待确认”，不进入标题、页面主张或上屏文字。

## 快速开始

```text
使用 $xhs-cast 把下面的材料规划成小红书卡片。

材料：[链接、文件或正文]
目标读者：[已知时填写]
希望读者完成的动作：[查看、安装、收藏、尝试等]
```

默认会先确认方向。需要跳过时，在请求中明确写出“跳过确认”“不用问”或“直接生成”。

## 2.0 的变化

| 改进 | 解决的问题 |
| --- | --- |
| 可知情的方向确认 | 每个选项说明适用场景、组织方式、最终交付和取舍，用户不必从方法术语里猜答案 |
| 交互与确认分离 | 支持原生控件、视觉面板和编号降级；没有回传时不会误判为已确认 |
| 新闻事实优先 | 先识别导语、栏目和具体条目，让读者只看标题也知道发生了什么 |
| 多主体机制分开处理 | 不把访问边界、动作权限、交付复核、研究方向和个人建议压成同一个结论 |
| 更明确的证据上限 | 同时检查来源层级、发布状态、可用范围和时间，避免把功能说明写成效果证明 |
| 标题与页面职责对账 | 封面概括整组，每页标题概括本页新增信息，正文直接解释或证明标题 |

## 完整文件结构

安装或发布时必须保留整个目录，不能只复制 `SKILL.md`：

```text
xhs-cast/
├── SKILL.md
├── README.md
├── agents/
│   └── openai.yaml
└── references/
    ├── marketing-communication-method.md
    └── marketing-translation-layer.md
```

`references/` 保存两份按需读取的方法文档：

- `marketing-communication-method.md`：营销传播判断
- `marketing-translation-layer.md`：把策略翻译成页面和文案

缺少这两个文件时，Skill 仍可能被加载，但无法完整执行 2.0 的策略与翻译规则。

## 安装位置

从 GitHub 下载或安装时，保留完整的 `xhs-cast/` 目录，再放入对应宿主的 Skill 目录：

- Codex：`~/.codex/skills/xhs-cast/`
- Claude Code：`~/.claude/skills/xhs-cast/`

使用 Skill 安装器时，也应选择包含 `SKILL.md`、`agents/` 和 `references/` 的完整目录。只复制 `SKILL.md` 会丢失 2.0 的详细方法和交互说明。
