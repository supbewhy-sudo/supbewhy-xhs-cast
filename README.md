# supɃewhY-XHS-CAST

> 当前主版本已纳入 2.0 规则：正式规划前确认方向，多主体先做机制归类，按来源层级、发布状态、范围、时间和主张类型控制证据上限。调用名为 `$xhs-cast`。

XHS CAST（小红书卡片策略工具）把选题、产品、教程、观点、案例或资源材料，整理成面向明确读者、阅读路径清楚、可以直接进入制作的多页卡片方案。

它不是标题生成器。标题协调只是规划完成后的质量检查；真正的工作是决定这组内容向谁传播、先讲什么、用什么证据、每页承担什么任务，以及读者最后做什么。

每次新的正式规划前先让用户确认内容类型、传播目标、TA、来源范围和 CTA；用户也可以在请求中明确跳过。确认后才生成完整策略、页序和逐页文案。

当材料包含多个主体或产品时，会先区分每条信号的对象、动作、机制层、来源层级、证据性质、发布状态、范围和时间。只有机制与证据可比时才做共同归纳，否则逐条对照，避免把“访问边界、动作权限、交付复核或研究方向”压成一个结论。

日报编辑总括、条目摘要和未核对的二手转述只用于定位和组织，不能冒充原始事实；公开 beta、试用、研究、招聘、公司自述部署和个人实测也不会被升级成普遍可用能力。证据会按“功能、输出、效果、可用性、风险或趋势”等主张类型匹配，而不是套用单一总排行榜。

## 能交付什么

- 紧凑的传播策略摘要：目标读者、核心价值、证据状态、阅读路径与 CTA
- 由解释难度决定的页数和页序，不按 README 章节或功能目录机械拆页
- 每页最终上屏文字、信息层级、构图意图、重点词、证据素材和承接
- 可交给 Guizang 等制卡工具继续制作的语义交接
- 用户明确要求时，生成与卡片使用同一主张和证据上限的小红书笔记

## 事实与证据边界

XHS CAST 不会为了让文案更像营销内容而补写用户故事、痛点、旧做法、疑虑、数据或效果。

- 材料没有提供的触发场景、当前替代和疑虑会标记为待确认。
- README 和功能清单只能证明产品被设计成做什么，不能独立证明实际效果。
- 没有案例或数据时，传播目标会降低为理解、查看、验证或尝试。
- 不把规划描述成已经完成的图片、外部验证或小红书发布。

## 适用场景

- 把 GitHub 项目、AI 工具、产品或服务介绍成小红书卡片
- 把教程、方法、观点、案例、复盘或资源清单重新组织成多页内容
- 现有卡片像功能目录、页序没有承接，或主张缺少证据
- 需要交付明确的上屏文字和制卡规格，而不只是几个标题

只需要单个标题时，应使用专门的标题工具。

## 安装

### Codex

```text
使用 $skill-installer 从 https://github.com/supbewhy-sudo/supbewhy-xhs-cast 安装 xhs-cast
```

也可以把仓库克隆到 `~/.codex/skills/xhs-cast`。

### Claude Code

把仓库克隆到 `~/.claude/skills/xhs-cast`。Claude Code 会在相关任务中自动加载，也可以输入 `/xhs-cast` 直接调用。

两个宿主使用同一个调用名 `$xhs-cast`；不要把当前使用的客户端自动写成产品唯一支持环境。

## 使用

```text
使用 $xhs-cast 把下面的材料规划成小红书卡片。

材料：[链接、文件或正文]
目标读者：[已知时填写]
希望读者完成的动作：[查看、安装、收藏、尝试等]
```

XHS CAST 会先给出一张方向确认单：已经明确的内容等待确认，缺失且会改变页序或主张的字段提供 2–3 个选项并允许自定义。只有当前宿主同时提供 `visualize` 和可用的 `window.openai.sendFollowUpMessage` 回传时，才使用可回传选择面板；否则使用原生选择控件或编号选项。面板创建失败、回传失败、超时或重复回传都不会被当作确认，按同一份编号确认单降级处理；“可以”“继续吧”等模糊短语也不算确认。把 XHS CAST 自己拆成介绍卡片同样走这一步；仅在用户明确说“跳过确认”或“直接生成”时除外。

确认后仍缺少的场景、替代、疑虑或证据会清楚标记待确认，不把猜测写进卡片。

## 输出结构

```text
传播策略摘要
└── 已确认事实、核心价值、证据状态、阅读路径、CTA、待确认项；多主体时附机制归类矩阵

整组页序
└── 每页的独立职责和标题

逐页规划
├── 页面任务、读者信息变化、来源锚点、事实归属/证据性质（不上屏）
├── 最终上屏文字
└── 构图、阅读顺序、重点词、证据素材、承接和 Recipe
```

## 一个不夸大效果的示例

假设材料只确认：一个工具能读取项目材料，输出小红书页序、上屏文案和制作交接，但没有真实用户案例。

合理的页面路径是：

1. 说明“从什么材料，得到什么可制作交付物”
2. 解释产品是什么，以及规划与机械拆章节的区别
3. 展示一次真实输入与实际输出
4. 说明能力边界和未被证明的部分
5. 提供准确安装或查看入口

封面应先说明读者任务或可证明交付，内部质量控制留在产品说明之后。仓库公开、许可证和使用成本也要分别核实。
