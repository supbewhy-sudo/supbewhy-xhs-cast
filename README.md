# XHS CAST 2.0

小红书卡片策略工具：把已有材料整理成读者看得懂、证据对得上、可以直接进入制作的多页卡片方案。

> XHS CAST 不是标题生成器。标题协调只是最后的质量检查；核心工作是决定让谁看、先讲什么、凭什么相信，以及读者下一步做什么。

## 它解决什么问题

很多卡片方案有材料，却仍然像功能目录：封面只讲一个局部，页面之间没有信息承接，标题听起来统一但读者看不出每页重点，结论也超过了材料能证明的范围。

XHS CAST 2.0 会先把传播方向说清楚，再决定页数、页序和文案。它特别适合以下任务：

- 把 GitHub 项目、AI 工具、产品或服务介绍成小红书卡片
- 把教程、方法、观点、案例、复盘或资源清单重新组织成多页内容
- 审查一份已有方案：封面是否概括整组、每页是否有独立职责、标题是否被正文兑现
- 把日报或新闻材料做成真正的快讯，而不是把“依据、原因、证据”当成事件标题

## 你会得到什么

一次完整规划通常交付四层结果：

1. **传播策略摘要**：目标读者、唯一传播目标、核心价值、证据状态、阅读路径、行动入口（CTA）和待确认项。
2. **整组页序**：由读者需要的信息变化决定页数，不按文档章节或功能列表机械拆页。
3. **逐页卡片方案**：页面任务、读者应获得的新信息、来源锚点、最终上屏文字、层级、重点词和承接动作。
4. **制卡交接**：构图意图、证据素材、制作限制和 Recipe，便于交给 Guizang 等制卡工具继续制作。

用户明确要求时，也可以生成与卡片使用同一主张和证据上限的小红书笔记。

## 使用流程

```text
提供材料
  -> 确认内容方向和交付取舍
  -> 建立来源与证据边界
  -> 设计读者路径，再决定页数
  -> 为每页确定职责，再写标题和上屏文字
  -> 做封面/页面标题对账与交付前检查
```

### 先确认方向

每次新的正式规划或完整重写，2.0 会先给一张方向确认单。确认单不只列术语，而是解释每个选项：

| 说明 | 用户需要知道什么 |
| --- | --- |
| 适用场景 | 当前材料为什么适合这个方向 |
| 内容组织 | 会按什么顺序，保留什么，舍弃什么 |
| 最终交付 | 选择后会拿到什么，读者看完能带走什么 |
| 关键取舍 | 与其他方向相比，重点和证据门槛如何变化 |

例如，日报材料可能出现以下三个方向：

| 方向 | 选了之后会怎么做 | 最终得到什么 | 主要取舍 |
| --- | --- | --- | --- |
| **新闻速览** | 按时间或原始栏目逐条讲清主体、动作、对象和状态 | 多页快讯；读者知道本期发生了什么 | 保留广度，单条背景较少；适合多条消息 |
| **单条深挖** | 只围绕一个主体或事件补背景、直接证据和边界 | 一条消息讲透的专题卡片 | 舍弃其他条目，换取单条理解深度 |
| **跨条目判断** | 先列出可比条目，再提炼有边界的共同判断 | 带证据和限制条件的趋势/判断卡片 | 证据门槛最高；不同机制不能硬合并 |

默认方向必须附上“为什么基于当前材料推荐”的理由。用户可以选择某个方向、修改字段、输入自定义方向，或明确要求跳过确认；没有明确确认前，不生成完整策略和逐页文案。

## 交互方式

交互行为与宿主能力匹配，不把某一种客户端当成唯一环境：

- 宿主有可回传的原生选择控件时，使用原生控件。
- Codex 运行时同时提供 `visualize` 和可回传当前对话的接口时，使用可点击的方向选择面板。
- 两者都不可用时，首次确实需要选择的任务会提示可安装/启用 Codex 的 `visualize`，同时立即提供编号选项继续；不自动安装，也不阻塞本次任务。
- 面板显示但无法回传、回传报错或超时，都按同一份编号确认单处理，不能把面板状态当成用户授权。
- Claude 等已经提供原生交互的宿主不显示 Codex 插件安装提示。

无论是视觉面板、原生控件还是编号版，选项的适用场景、内容组织、交付结果和取舍必须保持一致。

## 日报与新闻模式

新闻材料先区分三层：导语是编辑框架，栏目标题是分类，条目正文才是“谁在什么时间对什么对象做了什么”。

因此，新闻模式的主标题优先写事件事实：

```text
主体 + 具体动作/事件 + 对象或状态
```

“依据”“为什么”“证据性质”“应用”可以作为副标题或收尾，但不能替代条目事实。封面出现数量、主体数、时间范围或“这周/本期”等承诺时，2.0 会逐项对账到后续页面；无法对账就降低或删除承诺。

## 证据边界

2.0 会区分“功能被设计成这样”和“现实中已经产生了效果”：

- 原始帖子、官方文档、真实产物或原始数据，只支持明确范围内的对应主张。
- 日报摘要和编辑总括用于定位与组织，不自动证明细节、因果或行业共识。
- Beta、试用、研究、招聘、公司自述部署和个人实测，不升级成普遍可用能力。
- 没有案例、数据或独立评测时，不补写用户故事、效果数字或“更安全/更高效”等结论。
- 访问边界、动作权限、交付复核和研究方向属于不同机制，不能因为同一时间出现就压成同一种做法。

缺失的 TA 场景、当前替代、疑虑或证据会标记为“待确认”，不会进入标题、页面主张或上屏文字。

## 快速开始

把材料和希望读者完成的动作一起交给 Skill：

```text
使用 $xhs-cast 把下面的材料规划成小红书卡片。

材料：[链接、文件或正文]
目标读者：[已知时填写]
希望读者完成的动作：[查看、安装、收藏、尝试等]
```

正式规划前会先确认方向。只有在当前请求中明确写出“跳过确认”“不用问”或“直接生成”时，才直接进入策略和页序。

## 2.0 做了什么优化

相较于只关注标题和页面格式的旧工作方式，2.0 增加并固化了这些判断：

1. **方向确认可知情选择**：每个选项都说明适用场景、组织方式、最终交付和关键取舍，避免用户从“新闻速览/单条深挖”等陌生词里猜答案。
2. **交互与确认分离**：支持视觉面板、原生控件和编号降级；面板失败或没有回传时不会误判为已确认。
3. **新闻事实优先**：先识别导语、栏目和具体条目，让读者只看标题也能知道本期发生了什么。
4. **多主体机制不压平**：分开访问边界、动作权限、交付复核、研究方向和个人建议，只有可比内容才做共同归纳。
5. **证据上限更明确**：主张同时记录来源层级、发布状态、可用范围和时间，并按功能、输出、效果、可用性、风险或趋势匹配证据。
6. **标题与页面职责对账**：封面概括整组，每页标题概括本页新增信息，正文必须直接解释或证明标题；不再用统一标题形状代替清楚表达。

## 完整文件结构

发布或安装时需要保留整个目录，不能只复制 `SKILL.md`：

```text
xhs-cast/
├── SKILL.md
├── README.md
├── agents/
│   └── openai.yaml
└── references/
    ├── marketing-communication-method.md
    └── marketing-translation-layer.md
```

`references/` 保存两份按需读取的详细方法：一份负责营销传播判断，一份负责把策略翻译成页面和文案。缺少它们时，Skill 仍可能被加载，但无法完整执行 2.0 的策略与翻译规则，因此不应把不完整目录当成完整安装。

## 安装位置

从 GitHub 下载或安装时，请保留整个 `xhs-cast/` 目录，并放到对应宿主的 Skill 目录：

- Codex：`~/.codex/skills/xhs-cast/`
- Claude Code：`~/.claude/skills/xhs-cast/`

通过 Skill 安装器安装时，也要选择包含 `SKILL.md`、`agents/` 和 `references/` 的完整目录。只复制 `SKILL.md` 会丢失 2.0 的详细方法与交互说明。
